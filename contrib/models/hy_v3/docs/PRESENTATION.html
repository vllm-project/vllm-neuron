2 · 部署

每层的数据流与 HBM 预算

Prefill（序列并行）

  • 层间每个 rank 持有 chunk 的 1/64 个 token
  • attention 前 all-gather，算自己那个头（读这个请求已缓存的前缀），O 投影后 reduce-scatter 回到各 rank
  • router 和完整的 shared expert 在本地 token 上算；MoE 再 all-gather token 和路由权重，各 rank 只算自己 3 个专家，最后 reduce-scatter 合并
  • 每个 4096-token chunk：161 次 reduce-scatter，每次 128 MB

Decode

  • 每个 rank 持有全部 token；attention 算自己那个头 → all-reduce
  • router 复制；只算被路由到本 rank 的专家（moe_tkg_hits），token 多时算全部 3 个（moe_tkg）
  • shared expert 算 1/8；routed + shared 的部分结果合并成一次 all-reduce；每步 161 次 all-reduce
  • MTP k=3：每步 = 一个 target NEFF（每个请求验证 1+3 个 token，设备上 rejection sampling）+ 一个 draft NEFF（MTP 层跑 3 次）

3 · 数值精度

哪些是 FP8 运算，哪些是 BF16 / FP32

部分prefilldecode
QKV / O 投影W8A8：激活用静态 scale 量化成 FP8，FP8 × FP8W8A8（decode 融合 kernel，STATIC）
Shared expert、layer 0 dense MLPW8A8（CTE kernel：RMSNorm 后静态量化）W8A16：TKG kernel（≤ 96 token）要求 BF16 输入，BF16 × FP8
Routed expertsW8A16：moe_cte，BF16 × FP8（本次优化前先把权重 CAST 成 BF16）W8A16：moe_tkg 在 TRN2 上忽略 input_scale，BF16 × FP8
Attention 核心（QKᵀ、softmax、PV）BF16（FP8 KV 先复制成 BF16）kernel 直接读 FP8 KV；K / V 的 scale 并入 softmax_scale 和 O 投影的 scale
Router、RMSNorm、QK-normFP32 计算
Embedding、lm_head、MTP eh_projBF16
KV cacheFP8 E4M3，每层一个静态 K scale 和 V scale（checkpoint 不带，在 Neuron 上用 W8A8 模型标定，约 16 秒）；MTP 层单独标定

FP8 范围

checkpoint 是 OCP e4m3（最大 448），TRN2 kernel 的 e4m3 上限是 240。加载时所有 FP8 权重 ×0.5，scale ×2 补偿，对正常值是精确的。

和 GPU 的差别

Hopper/Blackwell 的 FP8 tensor core 要求两个输入都是 FP8，所以 GPU 上一般做 W8A8。TRN2 的 TensorE 可以直接做 BF16 × FP8，而且 decode 的小 batch 下 FP8 × FP8 并不更快，所以 MoE 保持 W8A16（见第 9 章的实测）。

5 · hy3-fp8-opt：MTP 投机解码

用 checkpoint 自带的 MTP 层当 draft

实现

  • 框架侧（单独的 PR）：vllm-neuron 新增 MTP proposer 和外部模型的注册钩子；target 把最后一层 norm 之前的 hidden state 交给 draft
  • 模型侧：draft 复用 decoder 层；每个 decode 步 = 一个 target NEFF（每个请求验证 1+k 个 token）+ 一个 draft NEFF（MTP 层跑 k 次）
  • draft 的 KV 也支持 FP8（MTP 层单独标定 scale）
  • verify 步是 4 × 并发个 token，所以 hits kernel 的上限设成 4 × (k+1)
  • 限制：MTP 和 DCP 不能同时开（已整理 issue 草稿）

8 · Sparse decode attention（实验性，默认关闭）

原理：先估算每个 KV 组的注意力上界，只读最可能重要的那部分

为什么能省

  • 85k、8 并发的 decode 步里，attention 占 55%，主要是读 8 × 85k 的 KV
  • 注意力权重通常集中在少数位置；摘要只有 KV 的 1/16，用它算上界，能以很小的代价找到这些位置

为什么只用在 decode

  • needle、长文档这类信息是在 prefill 时读进去的；prefill 保持 dense，精度风险小
  • 精度研究：只看 12.5% 的 block，needle 12/12，LongBench 与 dense 97% 一致；只保留开头 + 最近 block 的对照组，needle 0/12

参数

  • HY3_SPARSE_DECODE=0.125：86016 上下文的 decode bucket 有 2688 个 block，保留 512 个（向上取整到 256 的倍数）
  • 按组选：672 组里选 126 组，再加"最后一组"和"下一组"

8 · Sparse decode：实现

数据结构与每一步的流程

关键设计

  • batch < 4 时保持 dense：选择的开销基本固定（约 0.2 ms / 层），c1 时省下的 attention 不够抵消。但摘要每层都更新，保证并发上来时摘要是新的
  • 每 4 层选一次：所有层共用同一组物理 block，选出的 table 和 mask 直接给后面 3 层用
  • 历史之后的那一组必须在表里：MTP 的 verify token 跨 block 边界时，kernel 会经 block table 读回之前的 verify token
  • 保留的组可以任意顺序：attention 与顺序无关，不需要 sort

踩过的坑

  • torch 算子读了 kernel 也在读的张量（cos/sin、QKV 权重、norm gamma）会让 attention 结果出错 → 用自己的权重副本，按位置算 RoPE
  • 回收的 block 带着上一个请求的旧摘要 → decode 时也更新摘要（新开一组时重置）
  • table 宽度不是 256 个 block 的倍数时，kernel 会把 32-token block 再切小，压缩后的 table 会读错
  • 摘要每个 rank 约占 0.9 GB HBM → 去掉 32768 这个 decode context bucket
  • 4 层 mini 模型带 MTP 时，换一次编译都会翻转近似平局的 token → 精度只能靠完整模型判断

首版为什么慢 2 倍

  • 每层的选择是一串小的 torch 算子，在 Neuron 上每个都有固定开销：单核测整个函数要 1.07 ms（top-k 0.6、gather 0.25）

  • 单核测：NKI top-k 并不比 torch.topk 快，摘要 gather 本身已经是 DMA → 不写融合 NKI kernel，改为跨层复用选择

结论

  • FP8 × FP8 本身不更快：不开 double_row 时，速率和 BF16 × FP8 一样
  • double_row 用不上：它让 FP8 吞吐翻倍，但 decode 只有 ≤ 32 个 token，moe_tkg 靠 column tiling 把多条矩阵乘并排塞进 PE 阵列，比 double_row 还快约 2 倍；两者不能同时开。T = 4 时 double_row 直接编译失败
  • down 投影受装载权重限制：激活换成 FP8 没有可测的差别（就算有，每步约 9 万条 down 矩阵乘合计也不到 1 ms）
  • 所以 decode 改 W8A8 只会多出激活量化的开销，不实现；decode MoE 保持 W8A16（BF16 × FP8，本来就没有权重转换）

decode MoE 的瓶颈在哪

  • c5 profile：kernel 25.7 ms / 步，HBM 只用到约 187 GB/s，TensorE 忙 11.1 ms，Vector / Scalar 忙 12.8 / 7.6 ms
  • 瓶颈是每步约 42 万条小指令的开销和多引擎之间的等待，不是矩阵乘的算力

9 · W8A8（二）：prefill MoE 的实验

W8A8 不如"BF16 × FP8 直接相乘"

起因

  • 冷启动 prefill 的 4096 chunk 里，routed experts 79 ms，其中 Vector 引擎上的 CAST fp8→bf16 合计 63 ms：nkilib 的 shard_on_i_hybrid 对按通道 scale 的 FP8 权重，会先逐 tile 转成 BF16 再做 BF16 × BF16
  • 我们用的 hybrid kernel（比非 hybrid 快约 3 倍）不支持激活量化；非 hybrid kernel 只有 256×256 block 量化才走 FP8 × FP8

W8A8 版本怎么实现的

  • 新写一个 NKI 入口：沿用 hybrid 的静态 + 动态 block 循环，用 nkilib 的 compute_one_block 打开 block 量化和按 token 的激活量化
  • torch 侧按 token 量化：s = max|x| / 224，传入 x / s 和 s；每个专家的标量 scale 展开成 block scale
  • gate / up：FP8 × FP8（double_row）；down：BF16 中间激活 × FP8 权重

10 · Prefill attention

分段 attention 按 32-token block 逐个加载 V：找到了，还没修

现象

  • 完整命中 prefix cache 的 85k 请求，只有 23 个 token 要重算，但一次 prefill 仍要 460 ms（TTFT 约 0.73 s）
  • 其中 attention 311 ms；nkilib attention_segmented_cte 第 660 行，逐 block 发 V 的 DMA 占 254 ms：每层约 2656 次小 DMA，等效带宽约 3 GB/s
  • 23 个 token 被补齐到 512 的 prefill bucket，所以 attention 计算本身还有约 142 ms
  • 在 4 / 8 并发的混跑里，这些 prefill 会打断 decode，约占 TPOT 的 1/3

尝试与撤回

  • FP8 路径本来就会把请求的 KV 复制成连续的 BF16 → 把副本合并成 128-token block，V 的 DMA 次数降到 1/4
  • 效果：c8 TPOT 42.9 → 37.8 ms，吞吐 166 → 187 tok/s
  • 已撤回 needle 只过了 5/12：kernel 按 prior_tokens >> log2(block) 定位当前 chunk，要求已缓存的长度是 block 大小的倍数；而 prefix cache 按 32 token 命中
  • LongBench（prompt 互不相同）和 P/D 测试（命中长度恰好是 128 的倍数）都没暴露这个问题
  • 正确的修法：nkilib 按 token 偏移定位当前 chunk，再配合合并 block；属于框架 PR
