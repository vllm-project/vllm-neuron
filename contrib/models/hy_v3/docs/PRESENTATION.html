2 · 部署

一台 trn2.48xlarge：TP=64 + 完整 EP=64，SPMD

16 颗 Trainium2，64 个逻辑 NeuronCore（LNC=2），每个 24 GiB HBM，NeuronLink 互联（这台实例无 EFA）。一个 vLLM server，每个 NeuronCore 既是一个 TP rank，也是一个 EP rank，所有 rank 跑同一组 NEFF。

部分切分方式（64 个 rank）每个 rank 上
Embedding / lm_head（BF16）按 vocab 切分；采样在各分片上完成1,888 行 / 列
Attention（80 层）每个 rank 1 个 Q 头；每个 KV 头放在 8 个相邻 rank 上（KV 复制 8 份）QKV 4096×384，O 128×4096
Dense MLP（layer 0）intermediate 按 rank 切分208，补齐到 256
Router复制完整 4096×192
Routed experts（layers 1–79）EP：整个专家为单位，rank r 持有专家 3r、3r+1、3r+23 个专家，每层 56.6 MB
Shared expertprefill：每个 rank 一份完整副本；decode：另一份按 8 个 rank 一组切 8 份完整 + 1/8
MTP 层和 decoder 层相同；与主模型共享 embedding、lm_head、final norm

每层的数据流

  • Prefill（序列并行）：层间每个 rank 持有 1/64 的 token；attention 前 all-gather，O 投影后 reduce-scatter；MoE 再 all-gather token 和路由权重，各 rank 只算自己 3 个专家，最后 reduce-scatter 合并。每个 4096-token chunk 有 161 次 reduce-scatter（每次 128 MB）。
  • Decode：每个 rank 持有全部 token；attention 算自己那个头，all-reduce；router 复制；只算被路由到本 rank 的专家；routed 和 shared 的部分结果合并成一次 all-reduce。每步 161 次 all-reduce。

HBM 预算（每个 rank，85k、8 并发配置）

  • 权重 6.29 GiB（复制的 KV 头、router、shared expert 让它大于 checkpoint 的 1/64）
  • KV cache 13.47 GiB：FP8，每个 rank 存 1 个 KV 头 × 81 层，每 token 20.7 KB → 697k token = 8 个 86k 请求
  • NEFF 代码 2.21 GiB（随 bucket 数和 MTP 图增长）+ scratch 0.25 GiB
  • 合计约 22.4 / 24 GiB；KV_CAP 再高就放不下 decode NEFF

3 · 数值精度

哪些是 FP8 运算，哪些是 BF16 / FP32

部分权重激活实际计算
QKV / O 投影FP8FP8（静态 scale）FP8 × FP8（W8A8）
Dense MLP、shared expertFP8FP8（静态 scale）FP8 × FP8（W8A8）
Routed experts（decode，moe_tkg）FP8BF16BF16 × FP8（TRN2 上 kernel 不使用 input_scale）
Routed experts（prefill，moe_cte）FP8BF16BF16 × FP8（本次优化前会先把权重 CAST 成 BF16）
Router、norm、softmaxBF16/FP32FP32FP32
Embedding、lm_head、MTP eh_projBF16BF16BF16
KV cacheFP8 E4M3，每层一个静态 K / V scale（自行在 Neuron 上标定）；decode kernel 直接读 FP8；prefill 先复制成 BF16 再算

两处需要特别处理的地方

  • FP8 范围：checkpoint 是 OCP e4m3（最大 448），TRN2 kernel 的 e4m3 上限是 240。加载时所有 FP8 权重 ×0.5，scale ×2 补偿，对正常值是精确的。
  • KV scale：checkpoint 不带 KV scale。用服务化的 W8A8 模型在 BF16 KV 下跑校准集，读取 cache 里写入的 absmax 得到每层 scale（约 16 秒），并做成可分发的 profile；MTP 层也有自己的 scale。

和 GPU 常见做法的差别

GPU（Hopper/Blackwell）的 FP8 tensor core 要求两个输入都是 FP8，所以 MoE 一般做 W8A8。TRN2 的 TensorE 可以直接做 BF16 × FP8，所以 MoE 不量化激活也能省掉权重转换。实测 W8A8 版本反而更慢、误差更大（见后文）。

4 · 上游 hy3-fp8-contrib 分支

基础移植与第一批加速

移植

  • 自写的 static-FP8 模型（HYV3ForCausalLM），通过 vLLM plugin 注册，不改动 contrib 之外的文件
  • SP prefill、TP attention、EP MoE、DCP；在 0.29 上验证：4 层真实权重模型对 HF FP32 logits cosine ≥ 0.9993
  • MATH-500 no_think：97.0%

从 0.24 升级到 0.29

  • neuronx-cc 2.28 修复了"分段 attention + 带寄存器循环的 kernel 不能在同一个图里"的问题 → prefill MoE 可以用 hybrid kernel（动态 block 数），16k TTFT 4.40 → 2.61 s
  • prefill bucket 不再必须等于 KV 分段大小 → 多 bucket（512…8192），短 prompt 不再补齐到 2048
  • c=127、1k 输入：输出吞吐 378 → 773 tok/s

decode 只算被路由的专家

  • profile：batch 1 decode 中 routed experts 占 45%（12.6 / 27.8 ms）。每个 rank 都算自己的 3 个专家，但一个 token 的 8 个专家在每个 rank 上最多命中 1–2 个
  • moe_tkg_hits / _batch（从 nkilib 派生）：只读命中的专家权重，用运行时循环
  • c=1 TPOT 26.3 → 22.1 ms；c=4（4-token 步）52.1 → 34.1 ms，吞吐 +50%

长上下文与 FP8 KV

  • 256k 配置：DCP=8 把复制的 KV 头切成 8 份，KV 容量 260k → 2.08M token，8 个长请求并发；needle 12/12
  • FP8 KV cache：标定 per-layer scale + packed K 布局，KV 字节减半；有严格的验收门槛（精度、显存）
  • 固定的真实文本测试集：85k 输入、78k 共享前缀（92%），以及 prefill / decode 分开测的 P/D split 测试

5 · hy3-fp8-opt：MTP 投机解码

用 checkpoint 自带的 MTP 层当 draft

实现

  • 框架侧（单独的 PR）：vllm-neuron 新增 MTP proposer，以及给外部模型的注册钩子；target 把最后一层 norm 之前的 hidden state 交给 draft
  • 模型侧：draft 模型复用 decoder 层；每个 decode 步 = 一个 target NEFF（每个请求验证 1+k 个 token，在设备上做 rejection sampling）+ 一个 draft NEFF（MTP 层跑 k 次）
  • draft 的 KV 也支持 FP8（单独标定 MTP 层的 scale）
  • MTP 的 verify 步是 4×并发个 token，所以 hits kernel 的上限设成 4×(k+1)

限制：MTP 和 DCP 不能同时开（已整理 issue 草稿）。

8 · Sparse decode attention（实验性，默认关闭）

先做精度研究：decode 只看 12.5% 的 KV block，精度不变

方法（Quest 风格）

  • 每个 32-token block 保存 K 的逐维 min / max
  • 上界 max q·k ≤ relu(q)·max + min(q,0)·min，按上界选 top block；总是保留第一个 block 和最近的 block
  • 保留的 block 压缩成更窄的 block table，交给未改动的 decode kernel，kernel 只读这些 block
  • 只用于 decode；prefill 保持 dense（needle 这类信息是在 prefill 读进去的）

12.5%12/1219/1960%97%
只保留开头 + 最近 4 个 block（对照组）0/124/19

研究阶段的实现每一步仍读全部 K，只验证精度，不提速。对照组说明是"按上界选 block"保住了精度。

9 · Prefill：两处 kernel 问题

找到了两个热点，修好了一个

① 分段 attention 按 32-token block 逐个加载 V

  • 完整命中 prefix cache 的 85k 请求：一次 prefill 460 ms，attention 311 ms，其中 nkilib attention_segmented_cte 逐 block 发 V 的 DMA 占 254 ms（每层约 2656 次小 DMA）
  • 尝试：把 BF16 副本合并成 128-token block → c8 TPOT 42.9 → 37.8 ms
  • 已撤回needle 只过 5/12：kernel 按 prior_tokens >> log2(block) 定位当前 chunk，要求已缓存长度是 block 的倍数，而 prefix cache 按 32 token 命中
  • 需要改 nkilib（按 token 偏移定位当前 chunk），属于框架 PR

② Prefill MoE 先把 FP8 权重转成 BF16

  • 4096 chunk 里 routed experts 79 ms，其中 Vector 引擎上 CAST fp8→bf16 合计 63 ms
  • nkilib 的 hybrid kernel 不支持激活量化；用 block 量化路径做的 W8A8 版本：kernel 0.88 ms，误差 3.8e-2 不采用
  • 最终方案：拷贝 nkilib 的 kernel，关掉权重转换，让 TensorE 直接算 BF16 × FP8 → 输出逐位相同，单核 1.14 → 0.54 ms
  • 在图里：routed experts 79 → 53 ms/chunk，chunk 451 → 426 ms；c8 TPOT 42.9 → 41.4 ms 已提交 69d3cd5
